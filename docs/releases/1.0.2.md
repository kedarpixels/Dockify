## 1.0.2 (2026-11-08)

Projects as folders of apps, two backup tiers, project icons you can pick, and apps that reach each other by name.

### Added
- Every app answers to its name on its environment's network, so a frontend can call `http://backend:3020`. Before, only managed services had their name; built and image apps answered only to their `dk-<id>` address. The display name never becomes an address. An app takes its name on its next deploy.
- Two backup tiers per database: On this server (this server's disk) and Offsite (an S3 destination). Each has its own schedule, its own switch and its own number of backups to keep. When both are due together they share one dump, and each copy succeeds or fails on its own. Back up now writes to every tier that is on. The Backups tab and the Backups page show and edit both tiers.
- A project's Icon section is a dropdown: Automatic, which names the app it picks, each frontend with a fetched favicon, and the uploaded image while there is one.

### Changed
- A project is a folder of apps, and environments are optional. A new project starts with production only, and a project with one environment shows no environment tags, switchers or pickers anywhere. With two or more, the project header has an environment switcher. Settings adds and removes environments, and never removes the last one.
- Backups are kept by count: the newest N good automatic backups per tier. A failed run never counts, and the only good copy is never removed. Upgrading moves each database's schedule to the tier its destination names, with its cron, its switch and its old rule ("keep 3 and N days"). Clear the days in the schedule dialog to keep by count alone.
- On Automatic, a project's icon is the favicon of its most public frontend: the production frontend on a custom domain first, so an admin panel on a test domain no longer wins over the public site.
- Icon images fill their box with no background behind them, so transparent logos stay transparent.

### Fixed
- Each release made a Vercel project that builds the site from this repository try to deploy the releases branch and fail. That branch now tells Vercel not to deploy it.
- A deployment deleted on Vercel stayed in Dockify's list of an app that follows Vercel. Dockify now asks Vercel about it and removes it once Vercel confirms it is gone.
