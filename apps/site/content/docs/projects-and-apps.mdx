## The model

A **project** is a folder of apps: the frontends, backends, bots and databases one product runs. Its apps can come from different repositories, or from none.

```text
project            lighthouse   (branch main)
  app              web          frontend
  app              api          backend
  app              db           postgres
```

An **app** is one container: something you build, an image you pull, or a managed service.

That is all most projects need. **Environments** are an option, for running a second copy of the apps from another branch, such as `staging`:

```text
project            lighthouse
  environment      production   (branch main)
    app            web, api, db
  environment      staging      (branch staging)
    app            web, api, db
```

## Environments

A new project starts with one environment, `production`, on the instance's default branch (`main` unless you changed it under **Settings > Instance**). With one environment the dashboard shows none anywhere: no tags, no switcher, no environment picker. Variables are the project's own or an app's own, and each app shows its own branch.

To add one, open the project's **Settings** tab and choose **Add environment** in the Environments card. Give it a name and the branch that deploys to it; you can copy the variables of another environment to start from. It starts with no apps: add them with **New app**, which then asks which environment. Each environment gets its own apps, variables, domains and private Docker network, so `staging` apps cannot reach `production` ones. A project holds up to ten.

With two or more, the project page's header has an environment switcher (**All**, then one key per environment with its app count). It narrows the apps, deployments, domains and variables to one environment, and **New app** starts in the one you picked. App cards name their environment only when the cards on screen come from more than one. Lists that span projects, such as Resources, Domains and Logs, name an app's environment only for projects whose apps sit in more than one.

Removing an environment, from the same card, deletes everything in it: its apps and databases with their data, their volumes, domains and routes, and every variable set in it. Previews built from it close, and if it was the previews' base, they move to one that is left. Database backups stay on the Backups page until you delete them. You type the environment's name, and Dockify asks you to confirm it is you. It is refused while one of its apps is deploying (cancel or wait for it first), and the last environment can never be removed: delete the project instead. Removing down to one hides environments again.

Changing an environment's branch also asks you to confirm it is you, because it changes what code runs.

Inside an environment, apps reach each other by name. If your database app is called `db`, your api connects to `db:5432`; if your api app is called `api` and listens on 3000, your web app calls `http://api:3000`. Nothing outside the environment network can.

The name is the app's **name**, the lowercase one it was created with, never its display name, so renaming an app on the dashboard breaks no address. Only the running container answers to it: a release command or a scheduled job does not, so it never takes a share of the app's traffic. An app created before this rule answers to its name from its next deploy. A preview only reaches these names when it shares its base environment's network; see [Previews](/docs/previews#previews-and-production).

## App kinds

| Kind | What it is |
|---|---|
| `frontend` | A web app with a domain, built from your repository. |
| `backend` | An api or server, built from your repository or pulled as an image. |
| `bot` | A worker with no port, such as a Discord bot or a queue consumer. |
| `postgres` | Managed Postgres. See [Databases](/docs/databases). |
| `redis` | Managed Redis. |

## Sources

- **GitHub repository.** A repository and a branch. It builds from its Dockerfile when it has one, and otherwise with Railpack, with what it detected shown before you deploy.
- **Docker image.** Any image reference, by tag or digest. Private registries (GitHub Container Registry, Docker Hub, or your own host) are added once under **Settings > Integrations** and picked per app.
- **Database or service.** Postgres (17, 16 or 15) or Redis (8.2 or 7.4).
- **Compose import.** Paste a Compose file and Dockify proposes one app per service, listing everything it did not import, and why.

[Deploy sources](/docs/sources) has every field.

## Settings per app

| Setting | Notes |
|---|---|
| Start command | One line. Runs in place of the image's entrypoint, with no shell. Words starting with a flag go to the image's own entrypoint instead. Quotes, variables or `&&` need a shell in the image. Empty runs the image as built. The Dockerfile decides how the app builds. |
| Dockerfile path | Relative to the root directory. |
| Port | The port inside the container. Never published on the host. |
| Health check | Path, expected status, timeout, grace, interval. See [First deploy](/docs/first-deploy#health-checks). |
| CPU and memory limits | CPU from 0.1 to 64 cores, memory from 64 MB. With no CPU set, an app gets every core but one, at least 1. A pids limit is always set. |
| Release command | Runs once before traffic moves, for migrations. |
| Volumes | Named volumes only, up to ten. An app with a volume deploys stop then start. |

Changes to anything that alters what runs, or with what privilege (the release command, the root directory, extra capabilities, sysctls), ask you to confirm it is you. Capabilities come from a short allowlist (`NET_ADMIN`, `NET_RAW`), and sysctls only from `net.ipv4.*` and `net.ipv6.conf.*`.

### Start, stop and restart

An app's page has **Deploy**, **Restart** and **Stop**, and **Start** for a stopped app. Stopping and restarting ask you to confirm it is you, because they take an app down.

### What an app can never do

There is no field for any of these, and the worker checks the final container body again before Docker sees it:

- Publish a host port.
- Run privileged, or join the host's network, process or IPC namespace.
- Mount a host path or a device.
- Add capabilities outside the allowlist. Every container starts with all capabilities dropped except a fixed base set (CHOWN, DAC_OVERRIDE, FOWNER, SETUID, SETGID, KILL, NET_BIND_SERVICE), and `no-new-privileges`.

## Deploy targets

An app's target is either **server**, built and run here, or **vercel**, where the app stays on Vercel. By default Dockify only follows its deployments and logs. With **Deploy to Vercel** it also pushes the variables and asks Vercel to deploy. See [Vercel](/docs/vercel).

## Status page

Each project can publish a public status page at `/status/<project>`. The dashboard turns it on or off; its title, logo and app list are set through the [API](/docs/api). It shows current state and a daily history per app.

## Preview deploys

Every pull request can get its own copy of the project, `pr-<n>`, cloned from the project (or, with several environments, from a base environment you pick), with its own URL and low resource limits, asleep when idle and deleted on close or merge. See [Pull request previews](/docs/previews).

## Deleting

Deleting a project, an environment or an app asks you to type its name and to confirm it is you. Containers, volumes, routes, networks and the app's images are removed. Backups are not deleted with a database: they stay in the bucket, listed as orphans, until you remove them on purpose.
